# Playwright .NET

## Building

```bash
./build.sh --download-driver   # download the Playwright driver (needs Node.js/npm on PATH)
dotnet build ./src              # build the entire solution
```

## Running tests

Follow `.github/workflows/tests.yml` for the canonical sequence.

```bash
# Install browsers (pick one: chromium, firefox, webkit)
pwsh src/Playwright/bin/Debug/netstandard2.0/playwright.ps1 install --with-deps chromium

# Run tests
BROWSER=chromium dotnet test ./src/Playwright.Tests/Playwright.Tests.csproj -c Debug -f net8.0 --logger:"console;verbosity=detailed"
```

Tests take ~8 minutes. Always save output to a file and grep from there:

```bash
BROWSER=chromium dotnet test ./src/Playwright.Tests/Playwright.Tests.csproj \
  -c Debug -f net8.0 --logger:"console;verbosity=detailed" > /tmp/test-results.txt 2>&1
grep "^  Failed" /tmp/test-results.txt        # list failures
tail -5 /tmp/test-results.txt                  # summary
```

Run a single class with `--filter "FullyQualifiedName~PageWaitForUrlTests"`. Every `dotnet test` invocation is a fresh test host, so run a timing-sensitive repro a few times, on `main` and on the fix.

Test classes in `src/Playwright.Tests` mirror the upstream specs by name (`PageWaitForUrlTests` ↔ `tests/page/page-wait-for-url.spec.ts` in microsoft/playwright). Add a regression test to the matching class as a `[PlaywrightTest]` method; `PageTestEx` gives you `Page` and a local `Server` (`Server.SetRoute`, `Server.Prefix`, `Server.EmptyPage`).

The test adapters are not covered by `Playwright.Tests`. They are tested from the Node harness in `src/Playwright.TestingHarnessTest`: `npm ci`, then `TEST_MODE=nunit npx playwright test nunit.spec.ts` (`TEST_MODE` is one of `nunit`, `mstest`, `mstest.v4`, `xunit`, `xunit.v3`).

CI's style check is `dotnet format ./src/ --verify-no-changes`.

## Architecture

### Generated vs hand-written code
- Public API interfaces (e.g. `src/Playwright/API/Generated/IPage.cs`) are **generated** by `../playwright/utils/doclint/generateDotnetApi.js` from the upstream API docs. Do not hand-edit these — update the generator instead.
- The generator uses `classNameMap` for type mappings (e.g. `Disposable` → `IAsyncDisposable`, `boolean` → `bool`). Add entries there when a Playwright type should map to a different .NET type.
- The generator skips generating interface files for types like `TimeoutException` and `IAsyncDisposable` that map to built-in .NET types.
- Supplement interfaces (`src/Playwright/API/Supplements/`) are hand-written and extend the generated interfaces with .NET-specific overloads.
- Internal implementations live in `src/Playwright/Core/` (namespace `Microsoft.Playwright.Core`). These implement both the generated and supplement interfaces.
- Protocol types in `src/Playwright/Transport/Protocol/Generated/` are generated by `../playwright/utils/generate_dotnet_channels.js`. Both generators run as part of `./build.sh --roll <driver-version>`; a wrong doc comment, option name or overload in the .NET API is an upstream change to `docs/src/api/` or the generator and reaches this repo with the next roll.

### The client mirrors the JS client
- `src/Playwright/Core/*.cs` is a port of `packages/playwright-core/src/client/*.ts` in microsoft/playwright, method for method (`Frame.cs` ↔ `frame.ts`, `Waiter.cs` ↔ `waiter.ts`, `Connection.cs` ↔ `connection.ts`). Keep the same method boundaries, order of steps and log messages: reviews compare against the JS original, and rolls port upstream client commits one by one.
- Before restructuring a method, read its JS counterpart. If JS does the same thing, the change is compensating for something the .NET runtime does differently (usually threading, below); keep the deviation as small as the method allows and leave a comment naming the reason.
- If the same calls misbehave in the JS client, fix it upstream first.

### Threading model
The JS client is single-threaded and the other ports keep that model. .NET does not: the library and the user's code run concurrently, which is where "lost event" and "collection was modified" reports come from (#2719, #3207, #3364).

- `StdIOTransport` reads the driver's stdout on a dedicated long-running task and calls `Connection.Dispatch` for each message. `Dispatch` runs `ChannelOwner.OnMessage` synchronously on that thread, so `Frame.OnNavigated`/`OnLoadState`, the `Url` and `_loadStates` updates and every event handler user code attached (`page.FrameNavigated += ...`) run on the reader thread, and route handlers start there (until their first `await`). A handler that blocks (`.Result`, `.Wait()`) stalls all later messages, including the reply it is waiting for.
- Replies to commands complete a `TaskCompletionSource` created with `RunContinuationsAsynchronously`, so code after `await page.GotoAsync(...)` runs on a thread-pool thread while the reader keeps dispatching. JS guarantees that a continuation runs before the next message is dispatched; .NET does not.
- Outgoing messages are serialized through `Connection._queue` (a `TaskQueue` over a `SemaphoreSlim`). Incoming messages are not synchronized with user code.
- Sharing one `IPlaywright` across threads is not supported (#2560); use one instance per thread.

Consequences for changes:
- "Check state, then subscribe to the event" is correct in JS and a race here: the reader thread can deliver the event between the check and the subscription, and the wait times out (#3364). Subscribe first, then check, and unsubscribe when the check already passes.
- Do not add `lock`. The client has none. For state the reader thread mutates and user code reads, take a snapshot (`_frames.ToList()` in #2724, `_contextsForSelectors.ToArray()` in #3208) or use a concurrent collection (`ConcurrentDictionary` in `RouteHandler`, #2887).
- Adding or removing an event handler can send `updateSubscription` to the server: `ChannelOwner.UpdateEventHandler` does so for the first and last handler of `console`, `dialog`, `fileChooser`, `request`, `response`, `requestFinished` and `requestFailed`. `Waiter` subscribes through reflection (`GetEvent` + `AddEventHandler`).

### Key patterns
- All Playwright objects extend `ChannelOwner` and communicate via `SendMessageToServerAsync`.
- `Connection.cs` has a factory switch that creates the right `ChannelOwner` subclass based on `ChannelOwnerType`.
- New channel object types require: enum entry in `ChannelOwnerType.cs`, case in `Connection.cs`, initializer in `Transport/Protocol/Generated/`, and a `Core/` class.
- Public APIs should use .NET standard types (e.g. `IAsyncDisposable`) not custom Playwright types. Internal helpers (e.g. `Disposable` class in `Core/`) stay internal.
- Public API methods in `Core/` carry `[MethodImpl(MethodImplOptions.NoInlining)]`. `Connection.WrapApiCallAsync` walks the stack once per outermost API call to attach the user's frame to call logs and traces, and inlining breaks that walk (#2620). Keep the attribute on new public methods.

### Test adapters
- `Playwright.NUnit`, `Playwright.MSTest`, `Playwright.MSTest.v4`, `Playwright.Xunit` and `Playwright.Xunit.v3` each repeat the same hierarchy: `WorkerAwareTest` → `PlaywrightTest` → `BrowserTest` → `ContextTest` → `PageTest`. A change to one usually belongs in all five.
- Settings come from `.runsettings` through `Playwright.TestAdapter`: `PlaywrightSettingsProvider` is a VSTest `ISettingsProvider` for the `<Playwright>` section, and `PlaywrightSettingsXml` maps the XML onto the option classes by reflection. Microsoft.Testing.Platform does not run VSTest settings providers, which is behind most "runsettings are ignored" reports.

## Commit Convention

Before committing, run `dotnet format ./src/ -v:diag` and fix style issues.

Semantic commit messages: `label(scope): description`

Labels: `fix`, `feat`, `chore`, `docs`, `test`, `devops`

```bash
git checkout -b fix-39562
# ... make changes ...
git add <changed-files>
git commit -m "$(cat <<'EOF'
fix(proxy): handle SOCKS proxy authentication

Fixes: https://github.com/microsoft/playwright/issues/39562
EOF
)"
git push origin fix-39562
gh pr create --repo microsoft/playwright --head username:fix-39562 \
  --title "fix(proxy): handle SOCKS proxy authentication" \
  --body "$(cat <<'EOF'
## Summary
- <describe the change very! briefly>

Fixes https://github.com/microsoft/playwright/issues/39562
EOF
)"
```

Never add Co-Authored-By agents in commit message.
Never add "Generated with" in commit message.
Never add test plan to PR description. Keep PR description short — a few bullet points at most.
Branch naming for issue fixes: `fix-<issue-number>`

## Commits
- Do not include "co-authored" block in the commit message.
